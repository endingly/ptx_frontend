# TCGEN descriptor field and layout coverage

This API treats the [fixed PTX 9.3 Tables 43 and 45–48](https://docs.nvidia.com/cuda/archive/13.3.0/parallel-thread-execution/index.html) as encoded facts. A caller supplies a known 64-bit shared descriptor, 32-bit instruction descriptor plus explicit MMA kind, or 64-bit zero-column word. These value-owned words do **not** come from, authenticate, or track an opaque source register. The copy instruction's `TcgenCopyDescriptorView` instead borrows its owning resolved register and checks its source carrier; it does not decode the register's runtime contents. The two roles have separate lifetimes and claims.

`ptx_tcgen_descriptors.hpp` provides typed field queries and pure defined-field reports. A report separates field violations from facts still needed for conditional checks. It does not assert allocation state, buffer extent, actual memory layout, source-register values, producer ordering, or full MMA legality. Instruction and zero-column source-view types reserve their distinct roles for later selected MMA forms; this foundation does not add operand grammar or a source-value attachment.

Table 43 exposes 14-bit start, leading and stride encodings and their low-18-bit byte portions. Known bytes are checked for 16-byte alignment and the documented low-bit encoding relation, preserving higher address bits. Swizzle codes 0, 1, 2, 4 and 6 are recognized; 3, 5 and 7 are invalid. Fixed and reserved fields are checked independently. The eight documented relative K/MN rows are available as static symbolic layout data; their `T` factor means `128/element_bits` for the stated normalized representation and is not an invented packed 4/6-bit physical layout. Special code 1 has only its scoped MN 8×4 atom query, not a ninth relative row. Ordinary code 2/4/6 base-pattern checks require separately supplied repeating-pattern start. Fixed Table 44 does not give an unambiguous no-swizzle/code-1 base-pattern row, so those cases retain an applicability obligation.

Absolute leading mode requires encoded swizzle 2 and base offset 0. When known, K major, both transpose bits clear, exact cataloged `sm_103a`, and PTX at least 8.8 are checked. Missing target, major or instruction context remains an explicit obligation. This field check does not establish the actual K48 MMA tuple.

Tables 45–47 select fields from an explicit seven-kind identity rather than the word. Queries expose A/B/D type codes where encoded, scale IDs/types, sparse state, N/M envelope, saturation, transpose, negate, K choice and WS reuse. Defined-field validation enforces fixed/reserved fields and intrinsic type/scale/sparse-K rules. It does not turn dense sparse-selector bits or non-WS reuse into reserved fields, nor treat an encoded M/N envelope as a supported Table 42 MMA shape. Operational kind/shape/group/placement/target and source topology checks belong to the later MMA forms.

Table 48 exposes four start counts and first-span flags, zero-all, used/zero-column spans (encoded code plus one), and shift. With supplied M/N, active partitions are one mask for M128, two for M64, and four for M32, with N divided accordingly. The conditional shift maximum is 16 for M32 and 32 otherwise; absent M leaves its tighter check pending. Inactive count/flag fields are not reserved-zero. Zero-all does not bypass reserved bits36–38. Bits62–63 are **unclassified** by the fixed table: the report preserves them separately and never claims complete 64-bit descriptor validity.

The complete issue still requires accepted published review of this foundation and the final Tensor Memory coverage ledger. Offline assembly of an instruction cannot prove these caller-supplied bits match a runtime register or memory layout.
