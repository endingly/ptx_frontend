# TCGEN MMA frontend family coverage

The fixed [CUDA 13.3 / PTX 9.3 TCGEN MMA clauses](https://docs.nvidia.com/cuda/archive/13.3.0/parallel-thread-execution/index.html#tensorcore-5th-generation-instructions-tcgen05-mma) define four source families. In the current target catalogue, all **22 `(family, kind)` identities** below have canonical syntax, direct typed instruction classes, owned-module validation and conditional caller-known queries. This is frontend coverage of those fixed forms, not authentication of live descriptor bits or GPU execution. The [canonical source data](../../python/src/ptx_frontend/spec/resources/ptx_spec/tensor_memory_data_movement.yaml), [normalizer](../../python/src/ptx_frontend/spec/normalize/tcgen_mma.py), [operational rows](../../python/src/ptx_frontend/spec/tcgen_mma_operations.py), [descriptor fields](../../python/src/ptx_frontend/spec/tcgen_descriptor_domains.py) and [C++ emitter](../../python/src/ptx_frontend/code_gen/emit/tcgen_mma_operations.py) are the respective owners; the source census does not derive identities from the seven encoded descriptor kinds.

| --- | --- | ---: | --- |
| `tcgen05.mma` | f16, tf32, f8f6f4, i8, mxf8f6f4, mxf4, mxf4nvf4 | 30 | [f16](tcgen_mma_coverage.md), [tf32](tcgen_mma_tf32_coverage.md), [f8](tcgen_mma_f8f6f4_coverage.md), [i8](tcgen_mma_i8_coverage.md), [MX8](tcgen_mma_mx8_coverage.md), [MX4](tcgen_mma_mx4_coverage.md), [MX NV](tcgen_mma_mxnv_coverage.md) |
| `tcgen05.mma.sp` | the same seven kinds | 30 | [ordinary sparse](tcgen_mma_sparse_coverage.md), [sparse MX](tcgen_mma_sparse_mx_coverage.md) |
| `tcgen05.mma.ws` | f16, tf32, f8f6f4, i8 | 16 | [dense WS](tcgen_mma_ws_dense_coverage.md) |
| `tcgen05.mma.ws.sp` | the same four kinds | 16 | [sparse WS](tcgen_mma_ws_sparse_coverage.md) |

The 92 layouts count operand structure, not every CTA-group, selector, collector-action or target combination. The normalized source census expands these to 152 recorded topology tuples. Against its saved baseline of 40 tuples it finds 112 additions and no removals; 40 shared tuple keys also gained optional qualifier contracts. The census checks exact family/kind sets and 237 source assertions, while generated class identities and conditional checks have separate [C++ source/known-value tests](../../submod/resolved_ir/test/) and [Python catalogue tests](../../python/tests/spec/). These numbers describe the current fixed source model, not every spelling in later PTX versions.

Non-WS ordinary forms keep the kind-specific group, M/N/K, A placement, mask, D-scale, transpose and target rules. [A collector and ashift](tcgen_mma_a_collector_coverage.md) extend their eight dense/sparse identities without adding overlapping classes. All six dense/sparse MX identities share two A placements, typed selector provenance, scale-A/B Tensor Memory addresses and [A collector controls](tcgen_mma_mx_a_collector_coverage.md); they have no lane mask, D-scale or ashift. MX scale rows carry kind, sparse state, K, selector, role, factor count, allowed IDs and placement policy. MX8 omission derives 1X; MX4 omission derives block32; MX NV requires a written selector. The sparse MX query uses the actual sparse rows and their implicit F32 result: Tables 46/47 do not encode a D-type field. Its shared scale-row projection preserves dense versus sparse identity, so factor and ID checks select the matching rows.

Both WS families require CTA group 1 and expose B0–B3 collector controls with source omission distinct from written discard. Their optional final zero-column operand is a scalar 64-bit register; an independently supplied Table 48 word is checked only when that operand is present. Sparse WS also requires metadata after B and before `idesc`. The shared path rows select M32/G, M64/E or M128/D and require lane-half zero for applicable known A, D and metadata facts. Non-WS F/C half paths allow 0 or 16 and compare valid known halves; full paths require zero. D is checked even when A is shared. MX4/MX NV Python queries select their real K64/K96 row before this same lane rule, rather than inheriting the base f8 K32 path.

The [completion forms](tcgen_sync_coverage.md) contribute eight `tcgen05.commit` forms, two fences and two Tensor Memory waits to the frontend inventory. The exact instruction classes, typed completion identity, borrowed views and [conditional collector/history reports](tcgen_mma_a_collector_coverage.md) expose source and obligation information to a future analyzer. They do not run a sequence tracker or prove that a preceding fill, fence, barrier or allocation occurred. Ordinary source acceptance, owned reference/binding checks, target/version checks and caller-known word reports remain separate levels of evidence.

Known-value reports can reject inconsistent descriptor fields, shape/type/target combinations, sparse metadata indices, scale facts and lane claims. They **do not** prove that caller-supplied words equal opaque `idesc`, shared-descriptor, zero-column or Tensor Memory contents at runtime. The fixed Table 47 MX4 K96 scale-ID domain is 0/2, although later K96 diagrams depict 1/3; the frontend enforces the defined-word subset and records the conflict rather than inventing acceptance. The M32 sparse-WS metadata placement diagram is not established, so its report retains `MetadataLayoutRule`. Unscaled low-bit packing and some low-bit transpose rules remain explicit obligations where the fixed source does not settle a physical rule. Live sparse contents, scale placement across lanes, collector history, source stability until completion, allocation, synchronization and numerical results likewise remain unproved.

The final source snapshot was checked with Clang 21 Debug, Ninja and the configured LLD driver path. Complete CTest passed **1,357/1,357** tests, including **64/64** focused `TcgenMma*` tests; the Python CI suite passed **518/518**. All **13/13** installed MMA consumers configured, built and ran; a Python 3.14 wheel build, install and resource smoke passed. The generated plan contains **101 entries, 4,530 forms, 5,663 operand layouts, 913 multi-layout forms and 390 outputs** (11 global and 379 across seven categories). `GeneratorJobsTests.test_parallel_artifacts_match_serial_bytes_and_stable_manifest` checks the project's parallel-write/manifest protocol with synthetic emitters; `TcgenDescriptorGenerationTests.test_emitted_tables_are_deterministic_and_cover_literal_rules` checks TCGEN descriptor rows. Neither is a claim of independent byte comparison of all 390 outputs.

The first resolved-IR build in the integration sequence took **543.24 s** wall time with **4,146,040 KiB** peak child RSS; after the final core repair, an incremental resolved-IR build took **197.11 s** and **2,755,800 KiB**. These are different cache states, not a clean-build speed comparison. The latter full target build then took **11.93 s**, and full CTest took **106.40 s**. The fixed `ptxas` **13.3.73** checkpoint matched **31/31 expected probe outcomes**: 19 new kind groups, eight collector/ashift/zero-column controls, two exact-103a sparse-MX cases and two selector-omission controls (30 accepts and one intentional reject). It was not rerun in the final build, did not exercise every target or register spelling, and did not run on a GPU. The in-repository [source tests](../../submod/resolved_ir/test/test_tcgen_mma_sparse_mx.cpp), [known-row tests](../../python/tests/spec/test_tcgen_mma_sparse_mx_contract.py) and [installed consumer](../../examples/tcgen_mma_ws_sparse_consumer/) provide independently rerunnable positive and negative frontend evidence.

With the repository's configured vcpkg dependencies and Python test environment, the principal gates are:

```sh
cmake --preset ci-linux-clang-debug -DPython3_EXECUTABLE="$PWD/.venv/bin/python"
cmake --build --preset ci-linux-clang-debug
ctest --preset ci-linux-clang-debug --output-on-failure
.venv/bin/python -m unittest_parallel -s python/tests -t python -p 'test_*.py' --level=module --jobs 4 -v
```

The bounded assembler checkpoint used complete PTX 9.3 modules and `/usr/local/cuda-13.3/bin/ptxas`; its module/log package was retained separately from this repository. The documented 31/31 status is a recorded tool observation, while the commands above and linked tests are reproducible from this source tree. No release CI, public ABI freeze or simulator/GPU execution claim follows from these checks.
