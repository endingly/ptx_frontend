# Floating transcendental coverage

The generated model adds the explicit approximate forms of [sin](https://docs.nvidia.com/cuda/archive/13.3.0/parallel-thread-execution/index.html#floating-point-instructions-sin), [cos](https://docs.nvidia.com/cuda/archive/13.3.0/parallel-thread-execution/index.html#floating-point-instructions-cos), [lg2](https://docs.nvidia.com/cuda/archive/13.3.0/parallel-thread-execution/index.html#floating-point-instructions-lg2), and [ex2](https://docs.nvidia.com/cuda/archive/13.3.0/parallel-thread-execution/index.html#floating-point-instructions-ex2) from [PTX 9.3 §9.7.3.18–§9.7.3.21](https://docs.nvidia.com/cuda/archive/13.3.0/parallel-thread-execution/index.html#floating-point-instructions), the single-precision [tanh](https://docs.nvidia.com/cuda/archive/13.3.0/parallel-thread-execution/index.html#floating-point-instructions-tanh) from §9.7.3.22, and the half/bfloat [tanh](https://docs.nvidia.com/cuda/archive/13.3.0/parallel-thread-execution/index.html#half-precision-floating-point-instructions-tanh) and [ex2](https://docs.nvidia.com/cuda/archive/13.3.0/parallel-thread-execution/index.html#half-precision-floating-point-instructions-ex2) cohorts from §9.7.4.9 and §9.7.4.10. `.approx` is a typed fixed flag rather than an unchecked spelling, so an omitted mode cannot silently select the approximation. The frontend models parsing, owned resolution, and target validation; it does not execute numerical operations or compute approximation error bounds.

| Form | Minimum | Contract |
| --- | --- | --- |
| `sin.approx{.ftz}.f32`, `cos.approx{.ftz}.f32`, `lg2.approx{.ftz}.f32`, `ex2.approx{.ftz}.f32` | PTX 1.4 / all target architectures | Fixed typed `.approx`; optional `.ftz`; no rounding modifier. |
| `tanh.approx.f32` | PTX 7.0 / SM 75 | Fixed `.approx`; no `.ftz`, rounding, or saturation modifier. |
| `tanh.approx.{f16,f16x2}`, `ex2.approx.{f16,f16x2}` | PTX 7.0 / SM 75 | Fixed `.approx`; no `.ftz`. |
| `tanh.approx.{bf16,bf16x2}` | PTX 7.8 / SM 90 | Fixed `.approx`; no `.ftz`. |
| `ex2.approx.ftz.{bf16,bf16x2}` | PTX 7.8 / SM 90 | Fixed `.approx` and required typed `.ftz`. |

Every `.f32` cohort accepts a floating literal or a same-width native floating or bit register container in either position. The half and bfloat cohorts bind registers only: scalar `.f16` accepts `.f16` or `.b16`, packed `.f16x2` accepts `.f16x2` or `.b32`, and the BF16 forms require the `.b16`/`.b32` bit containers because `.bf16` is an instruction-only format rather than a `.reg` declaration format.

Integer literals and integer register containers, wrong widths, sinks, omitted `.approx` (the PTX 1.0–1.3 shorthand in which `sin.f32` meant `sin.approx.ftz.f32`), `.ftz` on any TANH cohort, `.ftz` on the F16 EX2 cohort, a missing `.ftz` on the BF16 EX2 cohort, and the unsupported `.f64` and `.f32x2` spellings are all rejected.

CUDA 13.3.73 `ptxas` evidence used `/usr/local/cuda/bin/ptxas -arch=sm_90 <module>.ptx -o <temporary>.o`. Its 44-module matrix had 23 expected accepts, 21 rejects, and no assembler divergence. The rejections are corroborated by the assembler's own diagnostics, which name the same contracts the model enforces: `.approx modifier required for instruction 'sin'`, `Illegal modifier '.ftz' for instruction 'tanh'`, `.ftz modifier required for instruction 'ex2.bf16'`, and `Unexpected instruction types specified for 'sin'` for `.f32x2`. Focused `-arch=sm_75` probes accept the PTX 7.0 TANH and F16 EX2 cohorts, and `-arch=sm_80` probes reject both BF16 cohorts with `Feature 'ex2.bf16' requires .target sm_90 or higher`, confirming the SM boundaries independently of the frontend tests. That assembler cannot demonstrate the PTX 1.4 floor or any pre-7.0 PTX version, so those PTX-version boundaries are enforced by frontend checker tests rather than assembler evidence.

Floating MIN/MAX and the audit of the existing ADD/SUB and mixed-family contracts remain the outstanding Issue 142 work. Neither gains execution semantics here.
